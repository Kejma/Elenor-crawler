# Устройство проекта

Запуск: `python main.py`. Редакторы запускаются прежними корневыми скриптами.
Внутренние импорты используют полные имена `elenor.*`; изменять `sys.path` не нужно.

| Каталог / модуль | Ответственность |
| --- | --- |
| `game/controller.py` | Создание игры, перезапуск и переходы между этажами |
| `game/loop.py` | Обработка событий, порядок обновления и вызов отрисовки |
| `game/combat.py` | Взаимодействие с целями, урон, способности, смерть и награды |
| `game/inventory.py` | Предметы, лут, экипировка, торговля и факел |
| `game/progression.py` | Выбор и применение улучшений |
| `game/narrative.py` | Мысли, журнал и реакции героя |
| `entities/` | Модели предметов, героя, врагов, объектов и движущихся эффектов |
| `world/dungeon.py` | Генерация, коллизии, пути и поле зрения |
| `puzzles/` | Правила оптики, генерация и состояние головоломок |
| `missions/` | Наполнение и сюжетные действия кампании |
| `rendering/renderer.py` | Композиция игрового мира и HUD |
| `rendering/assets.py`, `appearance.py`, `normals.py` | Процедурные изображения, внешность героя и карты нормалей |
| `rendering/lighting.py` | GLSL-программа и обмен данными с GPU |
| `rendering/mirrors.py`, `visibility.py` | Отрисовка механизмов и маскирование световых эффектов |
| `rendering/effects.py` | Частицы окружения, декали и FX-лаборатория |
| `ui/` | Меню, модальные окна, подсказки и перенос текста |
| `audio/` | Синтез звуков, пространственное аудио и музыкальный движок |
| `data/` | Реестры предметов и валют, формат и загрузка текстур |
| `localization.py` | Загрузка и объединение локализации |
| `profile.py` | Сохранения, настройки окна и преобразование координат |
| `paths.py` | Путь к корню ресурсов, независимый от текущей папки |
| `tools/` | Редакторы текстур и музыки, балансировщик, консоль разработчика |

Контроллер объединяет тематические mixin-классы. Это сохраняет существующий API
`game.*`, которым пользуются игра и редакторы, и отделяет крупные подсистемы без
переписывания игровых правил. Отрисовка модальных окон аналогично вынесена из
мирового рендера. Сохранена единственная реализация сброса профиля, которая
сохраняет настройки режима окна и разрешения.

## Луч и видимость

Луч больше не зависит от видимости его концов. Все сегменты рисуются на прозрачном
слое; лучи, рассеянный свет и блики зеркал затем целиком умножаются на маску поля
зрения и затухание текущих источников освещения. Середина луча видна самостоятельно,
скрытые стенами участки и тёмные края не прорисовываются. Слой компонуется перед
надписями и интерфейсными эффектами. Одна реализация маски используется с CPU и GPU.

## Производительность

- Оптическая трассировка кешируется до изменения зеркал, излучателя, блокирующих
  предметов или ревизии геометрии. Любое изменение стен/дверей должно вызывать
  `Dungeon.invalidate_light_cache()`, как и для обычного освещения.
- Поверхности маски переиспользуются; её освещённость считается на нативном размере
  мира, а не на увеличенном экране. Работа по каждому источнику ограничена его радиусом.
- Семь буферов CPU-освещения выделяются один раз и очищаются между кадрами. При
  размере 480×246 это устраняет повторное выделение примерно 3,15 МиБ за кадр.
- Перенос текста кешируется по тексту, шрифту и ширине; лимит — 256 записей.

В локальном микрозамере на неподвижной головоломке кешированное обновление занимало
около 0,0029 мс против 0,0070 мс при принудительном пересчёте. Это измерение одной
подсистемы, не оценка прироста общего FPS. GPU-производительность здесь не измерялась.

## Проверки и границы

`python -m unittest discover -s tests -v` проверяет генерацию и решение головоломок,
ключи, засады, награды, маску луча, кеши, сохранение настроек, импорты и ресурсы из
другой рабочей папки, а также реальные кадры игры, инвентаря, журнала и меню.

Редакторы текстур и музыки дополнительно проверены запуском с SDL dummy.
Тесты игрового рендера выполнены на CPU fallback. Вид луча в интерактивной игре и
работу драйвера OpenGL нужно проверить на машине игрока.

Большие графические функции и основной цикл остаются последовательными: они
зависят от порядка проходов и общего состояния кадра. Дальнейшие изменения их
алгоритмов стоит делать по профилю конкретной сцены. Форматы ресурсов и сохранений
не мигрируют; старый архитектурный документ сохранён как `legacy-design.md`.
