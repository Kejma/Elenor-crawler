# Elenor-crawler: архитектура и контекст для разработки с LLM

Актуально для состояния `main` после игрового коммита `6deafcc` от 17 ноября 2026.
Документ описывает существующий код, принятые решения и ограничения. При дальнейших
изменениях обновляйте соответствующие разделы. Если текст расходится с реализацией,
проверьте текущий код и историю Git: это описание снимка проекта, а не спецификация
всех будущих изменений.

Этот файл — основная точка входа для новой LLM. [legacy-design.md](legacy-design.md)
сохранён как исторический материал: старые пути, управление, число слотов и правила
пассивок из него больше не актуальны. [balance-audit.md](balance-audit.md) содержит
таблицы исходных оценок баланса и их ограничения.

## 1. Быстрый контекст и решения владельца

Проект — любительский 2D action roguelike / dungeon crawler на Python, Pygame,
NumPy и ModernGL. Действие происходит в реальном времени. Мир представлен тайлами,
но сущности двигаются в дробных координатах. Визуальный стиль — пиксельная графика
с отдельными картами нормалей, динамическим светом и тенями. Тон текстов —
мрачно-ироничный; герой комментирует происходящее мыслями и репликами.

Текущая игровая кампания — «Крысиный Погреб»: двор и таверна, деревянный погреб,
каменный подвал, пещеры и Крысиный Король. Генератор также имеет процедурный профиль,
но выбора новых кампаний в меню пока нет.

Решения, которые необходимо сохранять при разработке:

- Работать в `main`. Отдельные ветки создавать только по просьбе владельца.
- Четыре активные способности на Q/E/R/F. ПКМ не применяет способности.
- Пассивки временно упразднены; они вернутся после отдельной переработки.
- Сила, Ловкость и Разум должны отличаться стилем игры, а не только цветом урона.
- Любой вид оружия и активной способности может встречаться во всех пяти редкостях.
  Название/вид не должны означать обязательную «ступень мощности».
- Баланс стремится к сопоставимой полезности: учитываются урон, число целей,
  дальность, контроль, мобильность, защита, мана и риск применения. Равный DPS
  сам по себе этого не обеспечивает. Идеальный баланс пока не подтверждён.
- Игровой текст хранить в локализации; параметры предметов и способностей — в реестрах.
  Новые определения не добавлять в загрузчик локализации или корневой `main.py`.
- Обычный запуск игры и редакторов должен сохраняться после рефакторинга.

## 2. Запуск, зависимости и проверка среды

```bash
python -m pip install -r requirements.txt
python main.py
python texture_studio.py
python music_studio.py
```

Зависимости в `requirements.txt`: `pygame>=2.5.0`, `numpy>=1.26.0`,
`moderngl>=5.10.0`. Проверки последних изменений выполнялись на Python 3.12;
отдельной матрицы поддержки версий Python в репозитории нет.

Корневые скрипты — короткие точки входа, реализация находится в пакете `elenor`.
Скрипты можно запускать по абсолютному пути из другой рабочей папки. Ресурсы
находятся относительно `PROJECT_ROOT` из `elenor/paths.py`, а не текущего каталога.

ModernGL пытается создать контекст OpenGL 3.3. Если это не удаётся, `Renderer`
переключается на CPU-освещение NumPy. Наличие fallback не означает визуального
равенства всех эффектов GPU и CPU: туман, bloom и AO нужно проверять отдельно.

`python balance_mater.py` — старый инструмент, **перезаписывающий** файлы данных
баланса/предметов. Не использовать как безвредную проверку. Для отчёта есть:

```bash
python -m elenor.tools.balance_audit
```

Эта команда перезаписывает `docs/balance-audit.md`, включая вручную добавленные
после таблиц пояснения. Перед обновлением отчёта сохраните нужный комментарий.

## 4. Связи подсистем и владение состоянием

`GameController` наследует `NarrativeMixin`, `InventoryMixin`, `ProgressionMixin`,
`CombatMixin`. Mixin-классы не создают отдельные миры: все методы работают с одним
`self`, например `game.player`, `game.dungeon`, `game.mobs`. Это текущее устройство,
а не ECS, event bus или набор независимых сервисов.

```text
main.py → game.loop.main → GameController
                           ├─ Player / Item
                           ├─ Dungeon → mission.rats → объекты, враги, головоломка
                           ├─ Renderer + FXManager → CPU/GPU + UI
                           ├─ SoundSynth
                           └─ profile + localization + registries

use_or_equip_item → pending_action или немедленный execute
                 → CombatMixin._execute_skill_or_spell
                    ├─ spell cast_type → Projectile / visual_fx / бафф
                    └─ physical → execute_physical → physical_effects
                                                  → update_physical
                                                  → render_physical
```

Ключевые поля контроллера:

| Поле | Содержимое / кто использует |
| --- | --- |
| `loc` | Объединённые реестры и локализация; не только строки |
| `balance_data` | Загруженный `balance_table.json`; применяется не ко всем врагам |
| `profile` | Постоянные настройки и метапрогресс |
| `player`, `dungeon` | Текущий герой и этаж |
| `mobs`, `objects` | Живые `Enemy` и интерактивные `Interactable` |
| `projectiles` | Экземпляры общего `Projectile`, включая магические и оружейные |
| `physical_effects` | Словари физических действий: нож/склянка/рывок/капкан/визуал удара |
| `visual_fx` | Другие словари эффектов: кольца, молния, огненный след, пентаграммы, mana shard |
| `particles`, `popups` | Краткоживущие `Particle`, `FloatingPopup` |
| `mirror_puzzles` | Контроллеры головоломок этажа |
| `current_visible_tiles` | Текущий набор видимых клеток, не «память карты» |
| `cam_x`, `cam_y` | Камера в нативных мировых пикселях |
| `world_active` | Мир активирован действиями игрока; не равнозначно флагу паузы |
| `inv_open`, `levelup_choices`, `in_main_menu` | Режимы интерфейса и ограничения симуляции |

`reset_run()` создаёт нового героя из adjective/noun и генерирует первый этаж.
`descend_to_next_floor()` сохраняет героя, создаёт следующий этаж и перемещает его
на старт. `_populate_floor()` очищает списки объектов/эффектов текущего этажа,
вызывает миссию и собирает `solid_props`. Не добавляйте второй независимый список
врагов или предметов в рендерер: он получает состояние контроллера.

## 5. Один кадр, время и управление

Главный цикл находится в `game/loop.py`. Порядок важен:

1. `clock.tick(0)` и ограничение `dt` сверху 0,05 секунды; это переменный шаг,
   фиксированного физического тика нет.
2. Преобразование мыши из координат реального окна в логический холст.
3. Если открыто главное меню — отдельная ветка событий/музыки/отрисовки меню.
4. Игровые события: панели разработчика, клавиши, инвентарь, выбор улучшений,
   клики по HUD/миру, drag-and-drop.
5. Перемещение и отложенные действия `player.pending_action` (замах/каст/факел).
6. При активном мире, живом герое и отсутствии блокирующего UI:
   физические действия, реакции, ловушки уровня, AI, статусы, обычные снаряды,
   попадания и проверка смертей.
7. Таймеры героя и FX; для инвентаря/выбора улучшения/dev-панели в некоторые
   подсистемы передаётся `dt=0`.
8. Камера, FOV текущего кадра, обновление головоломок, освещённость героя.
9. Краткоживущие эффекты, осколки маны, построение списков света и HUD-света.
10. `Renderer.render_frame()`, панели инструментов, масштабирование в окно, flip.

Не следует считать, что единый флаг автоматически останавливает всё. У разных
эффектов есть собственные проверки паузы; при новом таймере надо явно определить,
должен ли он идти при инвентаре, повышении уровня, смерти и в меню.

| Управление | Текущее действие |
| --- | --- |
| WASD / стрелки | Движение |
| ЛКМ / пробел | Взаимодействие / обычная атака |
| Q / E / R / F | Активные слоты 0 / 1 / 2 / 3 |
| 1–4 | Пояс расходников; в окне выбора — соответствующая карточка |
| T | Факел |
| F5 | Перезапуск забега |
| I / Tab | Инвентарь |
| J | Журнал |
| Esc | Закрытие инвентаря / главное меню |
| F2 | FX-лаборатория |

ПКМ сохраняет контекстные операции интерфейса (например, выброс предмета),
но не применяет активную способность. Остальные отладочные клавиши проверяйте в
`tools/dev_panel.py` и `FXManager.handle_event()`: не занимайте их вслепую.

## 6. Координаты, сетка и масштаб

Источник истины — `config.py`, а не комментарии старого кода с размером 1152×858.

| Величина | Текущее значение |
| --- | --- |
| Тайлы | 16×16 нативных пикселей |
| Обычный спрайт | Обычно 16×20 |
| Карта | 66×42 клетки |
| Игровой вид | 30×13 клеток = 480×208 пикселей |
| Зона мыслей | Ещё 38 пикселей по высоте |
| Общий нативный холст | 480×246 |
| Увеличение | `SCALE=4`, nearest neighbour |
| Нижний HUD | 96 экранных пикселей |
| Логическое окно | 1920×1080 |

Сущности используют координаты в **клетках**, например `player.x=10.5`.
Конструкторы ряда моделей получают целочисленную клетку и добавляют 0,5;
`Interactable.x/y` обычно обозначают саму клетку. Учитывайте это при создании объектов.

Мировой пиксель: `wx = x * TILE_W`. Экранная координата игрового мира:
`screen_x = (wx - cam_x) * SCALE`. Камера — в нативных пикселях, не в клетках
и не в пикселях Full HD. При переменном размере окна добавляется ещё отображение
в `viewport_rect` из `profile.py`.

NumPy-буферы Pygame часто имеют порядок `[x, y]`, тогда как `dungeon.grid` — `[y][x]`.
Текстуры OpenGL требуют транспонирования/непрерывной раскладки: не удаляйте `.T`
и `ascontiguousarray` без проверки ориентации.

## 7. Реестры, локализация и профиль

### 7.1. Источники данных

- `data/items.py:BASE_ITEMS_DB` — игровые характеристики предметов.
- `data/abilities.py:ABILITIES` — характеристики активных способностей.
- `data/economy.py:CURRENCY_AND_GEMS_DB` — монеты и самоцветы.
- `entities/enemies.py:MOB_PROFILES` — базовые профили врагов.
- `missions/rats.py:_scale_mob_for_floor()` — дополнительное масштабирование кампании.
- `locales/ru/balance_table.json` — отдельный старый результат расчётов;
  `Enemy.apply_balance_profile()` используется в некоторых путях спавна.

`load_modular_locales()` сначала копирует реестры предметов и способностей,
добавляет валюту, затем загружает JSON из `locales/ru` в сортированном порядке.
`items.json` накладывается на предметы; остальные верхние секции объединяются
по ключам, включая поля уже существующей записи. Результат `game.loc['perks']`
содержит и механику, и текст.

Это не строгая схема валидации: локаль технически может перезаписать параметры,
а неизвестные item ID могут попасть в объединённый словарь. Держите новые числовые
поля в Python-реестрах. В загрузчике ещё есть старые точечные исправления текстов
`clear_mind`/`pyromaniac`; не используйте их как образец новой архитектуры.

Назначение локалей:

| JSON | Содержимое |
| --- | --- |
| `items.json` | Названия, описания, особенности предметов |
| `perks.json` | Названия, описания, боги активных способностей |
| `personalities.json` | Прилагательные/существительные героя, причуды, исходные статы и фразы |
| `ui_events.json` | Интерфейсные/событийные тексты |
| `rat_mission.json` | Данные текстов крысиной кампании |
| `prop_thoughts.json` | Реплики осмотра пропсов |
| `mirror_puzzle.json` | Сообщения механизмов головоломки |
| `mob_chats.json`, `skeleton_solo.json` | Диалоги и одиночные реплики врагов |
| `currency_and_gems.json` | Тексты/данные валюты и камней |
| `balance_table.json` | Старые расчётные балансные параметры, не обычная локаль |

Некоторые игровые сообщения ещё зашиты в Python. Разделение текста и механики
пока не завершено для всей базы; новое художественное описание добавляйте в JSON.

### 7.2. Профиль и сохранение

`profile.py` сохраняет JSON в `%APPDATA%/RatCellar/save_profile.json`; если APPDATA
не задана — в `~/RatCellar/save_profile.json`. Старый файл в корне проекта может
быть мигрирован при отсутствии нового. Это сохранение настроек и метапрогресса,
а не сериализация текущего этажа, боя или инвентаря.

Поля: банк, победа над Крысиным Королём/разблокировка крысолюда, внешний вид,
громкость, режим печати/частота мыслей, режим окна и разрешение.
`reset_profile_progress()` сохраняет настройки экрана и звука при сбросе прогресса.
Для тестов задавайте APPDATA во временную папку, чтобы не трогать профиль игрока.

## 8. Герой, инвентарь, экономика и оружие

`Player` создаётся из adjective/noun; базовые статы называются `body`, `cunning`,
`mind`. Внешний вид задаётся профилем отдельно от игровых характеристик.
Причуды вроде никтофобии, пиромании, ипохондрии, близорукости и накопительства
имеют ветки поведения в Player, InventoryMixin и NarrativeMixin. При изменении
причуды проверяйте все три места, а не только её описание.

Основные контейнеры:

- `inventory` — максимум 24 ячейки, доступное число задаёт `unlocked_slots`.
- `equipment` — `right_hand`, `left_hand`, `helmet`, `torso`, `boots`,
  `ring_1`, `ring_2`, `trinket`.
- `hotbar` — четыре ссылки на расходники, а не отдельные копии предметов.
- `ability_slots` — четыре экземпляра `Item` с типом `combat_skill` или `permanent_spell`.
- `perks` / `active_perks` — ID и уровни изученных активных способностей.

`remove_item_everywhere()` снимает ссылки на один экземпляр из контейнеров;
не удаляйте предмет только из кармана, если он ещё находится на поясе.
Переполнение при смене экипировки проходит через `overflow_drops` и
`_flush_overflow_drops()`. У двуручного оружия есть ограничения второй руки.

`Item` вычисляет статы экземпляра, в том числе зависимые от редкости. В оружии
есть `dmg_min/max`, `atk_cd`, `windup`, `reach`, `arc_deg`, `max_targets`,
`armor_pierce`, `multi_hit`, отбрасывание, криты, статусы, вампиризм, специальные
особенности и визуал метательного снаряда. `weap_style` влияет на поведение и вид.
Редкость оружия не должна быть жёстко привязана к его ID: `roll_weapon_drop()`
выбирает тип и редкость отдельно.

Обычный удар: `_perform_melee_attack()` → замах при необходимости →
`_execute_melee_swing()`. Метательное оружие использует общий `Projectile`;
рукопашный удар выбирает цели по дальности, дуге, LOS и лимиту целей. Учитываются
физическая защита, пробитие, крит, уязвимость/удар по неготовому врагу и эффекты оружия.
Не считать табличный урон окончательным уроном удара.

Экономика хранит стоимость в меди. `format_copper_Trigger()` переводит её в монеты
разных номиналов (10 медных = серебряная, 100 = золотая, 1000 = платиновая).
Самоцветы — физический лут с ценой; торговцы продают их через общий путь
`try_sell_gems_to_npc()`. Отдельно существуют осколки маны: это `visual_fx` с
притяжением к герою, а не обычный предмет инвентаря.

### 9.2. Применение, редкость и улучшения

`use_or_equip_item()` проверяет здоровье, занятость действием, ману и cooldown.
После замаха или сразу вызывает `_execute_skill_or_spell()`. Он определяет ветку
и силу, создаёт общий кредит роста вектора, затем направляет выполнение:

- `cast_type='physical'` → `game/physical.py:execute_physical()`;
- остальные `cast_type` → соответствующая ветка `CombatMixin`.

Физические навыки не требуют маны. Магические тратят MP. Масштабирование физических
навыков Ловкости использует `cunning` и `perk_phys_atk`, Силы — `phys_attack`;
магических — `mag_attack`. Старые поля `perk_*` остаются нулевой/служебной частью
расчётов, это не означает доступность пассивок.

В `roll_perk_choices()` вид способности и её редкость выбираются отдельно.
При изучении нужно передавать выбранную карточку в `Player.apply_perk()`, а не
повторно читать базовую запись с её исходной редкостью. Лимит — четыре разных
активных; уже изученные могут улучшаться. Пассивки не предлагаются и не изучаются.

`Item.base_stats` + `stat_bonuses_pct` позволяют пересчитывать улучшения от базы.
Бюджет начальной редкости: common 0%, uncommon 12%, rare 24%, epic 40%, legendary
60%, делится между `upgradable_stats`. Бюджеты повторных улучшений: 6/12/20/32/48%.
Cooldown уменьшается делением базы на `1+pct`, урон/обычные длительности растут
от базы. Есть особые правила для отскоков и длительности Омоложения.
Не менять общий бюджет и одновременно умножать уже улучшенное значение: это
создаёт непреднамеренный сложный процент.

`record_build_action()` ведёт `action_affinity` с противовесом между ветками и
общим затуханием роста. `get_build_affinities()` объединяет характеристики,
экипировку и изученные способности; это влияет на вероятность предложений.
Один `growth_credit={'action':(branch,amount),'awarded':False}` разделяется между
целями/тиками одного применения, чтобы не выдавать рост многократно.

### 9.3. Физические действия: состояние отдельно от картинки

`physical_effects` — список словарей. Общие поля: `kind`, `x/y`, `nx/ny`, `item`,
`power`, `credit`, `timer/max_timer`. Для ножа/склянки добавлены `speed`,
`remaining`, `total_distance`; для движения — оставшаяся дистанция и набор
задетых врагов; для капкана — задержка взведения.

- `execute_physical()` создаёт состояние; для ближних взмахов урон наносится
  здесь же после выполнения замаха, а короткая анимация живёт отдельно.
- `update_physical()` двигает снаряды/героя, проверяет столкновения, запускает
  капкан и удаляет завершённые действия. Перемещение разбивается на малые шаги.
- `burst()` создаёт настоящий газ через `FXManager.add_gas_cloud()` после
  завершения полёта склянки. Это не мгновенный круг в точке курсора.
- `rendering/physical.py:render_physical()` только рисует эти состояния.

Нож поражает первую цель и прекращает полёт. Склянка летит не дальше шести клеток,
останавливается стеной и оставляет облако. Новый капкан заменяет предыдущий,
срабатывает один раз после взведения. Таран и отскок проверяют коллизию героя
с учётом радиуса; таран может поражать несколько врагов, каждого один раз.

Стойка даёт `guard_timer`: входящий урон после защиты умножается на 0,55 с
минимумом единица, лечения нет. Отскок даёт `evade_timer` и ускорение.
Скрытность — `stealth_timer`, снижение заметности/шума и сброс преследования
ближайших врагов. Это не абсолютная невидимость и не неуязвимость. Атаки её
прерывают; ближний скрытый удар имеет отдельный коэффициент. Не путать это с
общим бонусом обычного оружия по неготовому врагу.

### 9.4. Что осталось от старой системы

В `Player` ещё присутствуют поля и ветки старых пассивок, в ProgressionMixin —
старый `update_auto_perks()`, в UI — вспомогательный код подсказок пассивок.
Они не являются доступной игровой системой: пассивные записи убраны из локали,
выбор их отклоняет, `apply_perk()` их не принимает, панель пуста, автообновление
не вызывается главным циклом.

В CombatMixin и renderer ещё есть старые пути `aoe_self`, `slam_cone`,
`whirlwind_slash`, `slam_wave`: актуальные физические навыки используют новый
`physical`-путь. Не исправляйте старый обработчик, ожидая изменения нового навыка.

## 10. Противники, статусы, смерть и награды

`Enemy` создаётся из `MOB_PROFILES`. Основные параметры: HP, скорость, диапазон
урона, защиты, дальность обнаружения, perception, ranged/boss/size flags, XP.
Состояния ИИ включают сон, еду, патруль, разговор и бой. Обнаружение связано
с дистанцией, освещённостью игрока, состоянием и скрытностью; шум может разбудить
или насторожить врага. Бой использует LOS и A* со своим таймером обновления пути.

`apply_status()` и `update_ai()` обслуживают poison, bleed, burn, slow, root, stun.
Статусы хранятся таймерами; периодический урон проходит в обновлении врага.
Крысы-сектанты/босс имеют каст пентаграммы, который затем обрабатывается эффектом
главного цикла. Источник урона сохраняется для корректного запрета роста от
уклонений против безнаградных врагов.

`_check_mob_death()` — общий путь удаления врага, крови, наград и сюжета босса.
Вызывайте его после урона: одного изменения `mob.hp` недостаточно. Защитная
проверка принадлежности `m in game.mobs` предотвращает повторные награды.

Особый контракт засады головоломки: начиная с четвёртого созданного врага
`no_rewards=True`, `xp_value=0`. Это отключает опыт, лут, mana shards и рост
векторов, включая физические/магические попадания и уклонения. Отложенные облака,
снаряды и ловушки должны сохранять атрибуцию; новый путь урона не должен обходить
этот запрет. Это не отмена боевых свойств оружия как таковых.

Масштабирование неоднородно: миссия вызывает `_scale_mob_for_floor()`, некоторые
дополнительные спавны — `apply_balance_profile()`. Меняя баланс врага, сначала
проследите реальный путь его создания. Изменение одного `balance_table.json`
не гарантирует изменение сюжетной комнаты.

## 11. Подземелье и кампания

`Dungeon.generate()` создаёт геометрию, двери, рычаги, освещение и зоны атмосферы.
`populate_mission_floor()` отдельно размещает мебель, NPC, лут, врагов и механизмы.
Миссия не должна создавать второй генератор сетки поверх текущего.

Текущие коды сетки: 0 — каменный пол, 1 — каменная стена, 2 — вода, 3 — трава/мох,
4 — деревянный пол, 5 — деревья, 6 — деревянная стена, 7 — скальная стена,
8 — пещерный грунт, 9 — дорога. Рендер отображает их на asset role ID;
код сетки не всегда совпадает с числом в имени `floor_*`.

`is_blocking_move()` учитывает сетку, двери, `solid_props` и невидимые границы.
`is_blocking_sight()` проверяет стены и закрытые двери; например, деревья
блокируют ходьбу иначе, чем квадратные каменные стены блокируют свет.
`has_line_of_sight()` — отдельная трассировка между точками.

`find_path()` имеет ограничение `max_expanded` и может вернуть **частичный** путь.
Для требования «обязательно достижимо» нельзя проверять только `if path`: проверьте
его последнюю клетку или используйте полный обход компоненты.

Кампания:

1. Двор, лесная дорога и таверна: Гуго, мебель, стойка оружия, лестница.
2. Деревянный погреб: крысы, лут, бочки, торговец.
3. Каменный подвал: сектанты, охрана, больше опасностей.
4. Пещеры: компактная вводная зеркальная головоломка, Крысиный Король, алтарь.

Код для `floor_num>=4` продолжает пещерную логику. Это не означает, что следующие
кампании уже спроектированы или имеют полноценное отдельное прохождение.

## 12. Зеркальная головоломка

Два явных профиля:

- `Dungeon(puzzle_profile='rats')` — используется GameController; вводный зал 11×9,
  работающий излучатель, без ключевого поиска и засады, перед боссом.
- `Dungeon()` / `procedural` — на подземных этажах шанс 12%, зал растёт до 17×15,
  перегородки и больше отражений, отдельная область с сундуком за решёткой.
  Лестница остаётся в обычной области.

`mirror_puzzle_info` содержит прямоугольники, вход, дверь-решётку и профиль;
`pre_boss_puzzle_info` сохранён для совместимости вводного режима.
Зона резервируется до обычной генерации. Коридор прокладывается в обход,
чтобы не прорезать второй доступ в запертую область.

`setup_mirror_puzzle_in_room()` строит схему. Есть вращаемые, двусторонние и
передвижные зеркала на рельсах. Генератор проверяет оптическое решение,
нерешённое начальное состояние, доступ к механизмам и сторонам толкания.
При неудачных попытках существует простая запасная схема.

Излучатель: `ready`, `need_lever`, `need_lens`. Ключевой рычаг или
`focusing_lens` размещаются в доказанно доступной части этажа при закрытых решётках.
Если безопасного места нет, излучатель становится готовым; недостижимый ключ
не подставляется «рядом со стартом» наугад. Линза — `quest_key`, исключена из
основного и запасного пула случайного лута.

`recalculate_mirror_puzzle()` трассирует лучи с защитой от циклов. Решение
защёлкивается: дверь не закрывается от следующего поворота зеркала. Обновление
оптики кешируется по зеркалам, излучателям, препятствиям и ревизии геометрии.
После изменения стен/дверей вызывайте `invalidate_light_cache()`; после изменения
геометрии для GPU также обновляйте сетку стен FX.

Обычная головоломка с третьего яруса может иметь засаду (35%): до трёх живых
врагов на контроллер, спавн после посещения зала, рядом с ним, вне актуального
FOV/прямой видимости, на свободной клетке с полным путём к игроку. Счётчик созданных
врагов не сбрасывается при уходе; решение останавливает спавн.

## 13. Отрисовка: где менять картинку

### 13.1. Быстрый указатель

эффективность способности.

### 13.2. Свет, глубина и слои

Рендер строит diffuse, normal и emissive холсты и буфер `entity_y_canvas`.
Плоские объекты пола рисуются до Y-сортировки; объёмные сущности сортируются по
положению ног. Буфер глубины нужен для света/перекрытий, а не для коллизий.
GPU получает холсты, FOV, стены, световые маски и облака. CPU fallback вычисляет
множители света NumPy. После освещения нативный холст увеличивается nearest neighbour.

Источник света — словарь с `pos`, `radius`, `color`, при необходимости
`allowed_tiles`, `foot_y`, `ignore_depth`. В render-списке позиция источника
относится к нативному виду; регистрация мирового света в `loop.py` выполняет
преобразование камеры и отдельно подготавливает HUD-свет.

`compute_nox_fov()` использует 280 векторизованных лучей. Возвращает:

- `fov_mask` — попиксельную маску холста;
- `visible_tiles` — видимые клетки, включая видимые границы стен;
- `player_open_tiles` — видимые открытые клетки для совместных масок света.

Это разные данные. Нахождение в `visible_tiles` само по себе не гарантирует,
что точка достаточно освещена. Проверка лишь начала/конца длинного луча ошибочна.

Светящиеся слои зеркал и физических действий рисуются отдельно, затем
`overlay_visibility()` учитывает FOV и затухание источников, а `mask_overlay()`
умножает alpha всего слоя. Поэтому видимая середина луча не зависит от источника,
а тёмные/закрытые участки не раскрываются. Эти слои располагаются до надписей.
Старые прочие overlays ещё имеют собственные правила; не предполагайте, что
маска автоматически применяется к любой новой графике на `screen`.

### 13.3. FXManager — не только отрисовщик

`FXManager` владеет облаками, декалями, пылью и лабораторией. `update()`
ядовитого облака также наносит урон и вызывает проверку смерти. При добавлении
эффекта через него нужно учитывать этот игровой побочный эффект.

Облако склянки хранит `growth_credit`, проверяет LOS до цели и не накладывает
дополнительно второй суммирующийся poison DOT. Другие старые облака могут иметь
иной путь нанесения урона. Не удваивайте урон, вызывая и старый, и новый путь.

## 14. Ассеты, карты нормалей и редактор текстур

`make_pair()` создаёт `(diffuse_surface, normal_surface)`. Для обычной сущности
типичный размер 16×20, пола/оверлея 16×16; у крупного босса обычно 32×36.
Высокие деревья и крупные декорации имеют отдельные размеры — проверяйте каталог.

Непрозрачные пиксели нормали приводятся к `NORMAL_COMPASS` через
`enforce_crisp_rim_normals()` / `quantize_normal_surface()`:

| Ключ | RGB | Направление |
| --- | --- | --- |
| flat | 128,128,255 | Плоская поверхность / +Z |
| up | 128,218,200 | Верхняя грань |
| down | 128,38,200 | Нижняя грань |
| left | 45,128,200 | Левая грань |
| right | 210,128,200 | Правая грань |
| up_left | 65,195,195 | Верх-лево |
| up_right | 190,195,195 | Верх-право |
| down_left | 65,60,195 | Низ-лево |
| down_right | 190,60,195 | Низ-право |
| deep | 128,128,155 | Шов / впадина |

Для горизонтальной поверхности мебели основная площадь должна оставаться flat,
иначе свет может сделать стол/кровать чрезмерно тёмными с некоторых сторон.
Повороты и отражения должны преобразовывать не только diffuse, но и нормали:
используйте `rotate_normal_pair()` / `flip_normal_pair_x()`, а не голый flip RGB.
У случайно вращаемых полов избегайте случайного изменения направления освещения.

`.dtex` — JSON с палитрами и закодированными строками пикселей. Версия 2 хранит
до трёх кадров, fps, random_rot, size, role_id, category; первый кадр также
продублирован в верхних полях ради совместимости с v1. `ASSET_CATALOG` задаёт
роли/размеры; manifest связывает ресурсы. `bootstrap_assets_if_needed()`
создаёт недостающие исходные ресурсы, `load_custom_dtex_animations()` загружает
пользовательские пары и анимации. Уже существующий `.dtex` может перекрыть новую
процедурную картинку — проверьте это, если правка assets.py «не видна».

Редактор текстур использует общий `CanvasHistory`, flood fill, live-light preview,
экспорт/импорт PNG и тот же формат `.dtex`. Не менять формат только со стороны
игры: нужен совместимый reader/writer и редактор.

## 15. Звук, музыка, мысли и журнал

### Звук и музыка

`SoundSynth` синтезирует SFX и управляет воспроизведением. Для событий героя и UI
обычно используется `sfx.play()`, для событий мира — `game.play_spatial()` /
`sfx.play_spatial()`, чтобы учитывать положение игрока, дистанцию и препятствия.
`GameController` дополнительно ограничивает частоту одинаковых звуков; у AI
есть собственные задержки. Не обходить их массовыми вызовами в каждом кадре.

`audio/music.py` содержит `PatternData`, `SongData`, `SynthVoiceEngine`,
`MusicLoopCompiler`: редактирование паттернов, голосов, компиляция петли/песни.
`tools/music_studio.py` — UI редактора. `music/` хранит композиции JSON.
Меню запускает свою петлю и затухание, миссия — пространственную тему босса;
FX-лаборатория имеет дискотеку. Смена этажа/забега останавливает соответствующие
петли, чтобы они не продолжались в чужой сцене.

### Мысли и журнал

`NarrativeMixin` разделяет важные события и фоновые реплики. Важная мысль
захватывает приоритет примерно на 4 секунды; следующие важные сообщения стоят
в очереди. Фон зависит от настроек частоты, cooldown и вероятности. Текст
постепенно открывается через `target_thought`, `shown_chars`, `update_typewriter()`.
Не заменять очередь одной записью ради нового события: потеряются сюжетные реплики.

`pick_text()` выбирает фразы без немедленного однообразного повтора и форматирует
параметры через `_SafeFormatDict`. `trigger_event_thought()` связывает события
с локалью. `update_world_reactions()` отслеживает увиденные объекты, опасность,
темноту, огонь и особенности героя. Журнал хранится в памяти забега, содержит
категории combat/event/speech и фильтры; это не файл сохранения.

## 16. Оптимизации и проверяемые ограничения

Существующие оптимизации:

- Кеш оптической трассировки по состоянию механизмов/препятствий/геометрии.
- Переиспользование семи CPU-буферов освещения и поверхностей маски.
- Маска эффекта считается на 480×208, а не на Full HD; расчёт каждого источника
  ограничен его радиусом.
- `wrap_lines()` использует LRU на 256 записей; иконки кешируются по имени/размеру.
- Renderer кеширует варианты героя, поворотов, отражений, tint/flash и emissive.
- A* врагов не пересчитывается для каждого кадра безусловно; FOV векторизован NumPy.
- Свет ограничивается списками/лимитами GPU, звуки — гейтами частоты.

При новой динамической картинке не менять общий кешированный Surface in-place,
иначе изменятся все пользователи этого ассета. При изменении стены/двери вызывать
`Dungeon.invalidate_light_cache()` и при необходимости `fx.rebuild_wall_grid()`.
Сигнатура оптики не замечает произвольных правок `grid` без инвалидирования.

Старый локальный микрозамер оптики давал около 0,0029 мс с кешем против 0,0070 мс
с принудительной трассировкой. Это результат одной сцены/функции, не доказательство
роста FPS во столько же раз. GPU-производительность и одинаковый вид на разных
драйверах не измерены. Не переносить исторические оценки FPS из legacy в обещания.

Сохраняющиеся архитектурные ограничения:

- Большие `render_frame()` и `main()` всё ещё последовательны и зависят от порядка.
- `visual_fx`, `physical_effects`, облака и обычные Projectile — разные контейнеры
  с разным жизненным циклом. Единого менеджера всех действий нет.
- Не все строки вынесены из Python; часть комментариев и неактивных веток устарела.
- Нет полной схемы валидации реестров/локалей и единого источника масштабирования мобов.
- Скрытность пока простая: таймер, заметность, шум и сброс состояния, а не полноценная
  система поиска последней известной позиции.
- Некоторые атаки ближнего боя наносят урон при выполнении действия; визуальная
  фаза не представляет непрерывный swept-hitbox оружия.
- Физические анимации процедурные и требуют оценки владельцем в игре; наличие
  теста на непустую поверхность не доказывает художественную готовность.
- Полный баланс четырёх активных слотов и сочетаний редкости не подтверждён прохождениями.

## 17. Типовые изменения: что трогать вместе

### Добавить/переработать активную способность

1. Определить её роль в ветке и отличия от существующих действий.
2. Добавить механику в `ABILITIES`: ID, branch, cast_type/shape, параметры,
   icon, upgradable_stats. Не назначать виду единственную допустимую редкость.
3. Добавить текст под тем же ID в `locales/ru/perks.json`.
4. Для физического действия изменить execute/update в `game/physical.py`,
   для заклинания — соответствующий cast_type в `CombatMixin`.
5. Подключить визуал в правильном рендерере и glyph в `ability_icons.py`.
6. Проверить изучение/апгрейд/стирание, четыре слота, отмену/паузы/смерть,
   геометрию, атрибуцию наград, редкости и понятность картинки.

### Добавить оружие

1. `BASE_ITEMS_DB` + название/описание в `items.json`.
2. Корректный slot, weap_style, диапазон урона, cadence, reach, arc, лимит целей.
3. Проверить общую модель Item, melee/thrown-путь и визуал снаряда/иконки.
4. Проверить случайный лут всех редкостей, двуручность, статусы и вывод сравнения.
5. Обновить расчётный отчёт с учётом того, что DPS не оценивает utility.

### Добавить пропс / врага

1. Создать procedural asset и при необходимости запись `ASSET_CATALOG`/`.dtex`.
2. Для твёрдого пропса обновить `SOLID_INTERACTABLE_KINDS`; зеркало использует
   отдельный `MIRROR_SOLID_KINDS`. Проверить движение, тень и запись глубины.
3. Взаимодействие: общий объект — CombatMixin, сюжетный — модуль миссии.
4. Текст осмотра — локаль; размещение — populate миссии/соответствующий генератор.
5. Для врага — MOB_PROFILES, AI/спрайт при новом поведении и реальный путь скейлинга.
6. Проверить сохранение доступности проходов, отсутствие ключей за решёткой,
   source/no_rewards и инвалидирование геометрии при изменениях.

### Изменить UI/управление

Изменять вместе `loop.py`, прямоугольники/подписи HUD, карточки/подсказки,
README и тест клавиатурных маршрутов. Не оставлять старые F/R или лимит 2 в UI.
Системные мышь/экран проходят через `profile.py`; не смешивать координаты окна
с координатами игрового мира.

## 18. Проверки перед передачей изменений

```bash
python -m unittest discover -s tests -v
python -m compileall -q elenor tests
```

При наличии отдельно установленного Ruff:

```bash
ruff check elenor --select F821,F811 --exclude __init__.py
git diff --check
```

На состоянии `6deafcc` — 34 unittest-проверки. Они используют SDL dummy, CPU fallback
и временный профиль. Перечень расширяется вместе с механиками; не поддерживайте
число тестов как фиксированную «норму».

| Набор | Что проверяет |
| --- | --- |
| `tests/test_mirror_puzzles.py` | Генерация/решение, доступность ключей, отсутствие обхода, засада, награды, кеш |
| `tests/test_abilities.py` | Наборы/иконки, изучение/редкость/слоты, попадания, нож/склянка, капкан, стойка, стены, эффекты |
| `tests/test_rendering_and_structure.py` | Импорты/пути, профиль, маски, кеш текста, реальные кадры экранов, Q/E/R/F и ПКМ |

После проверки логики нужна ручная проверка в игре: заметен ли замах, понятна ли
область удара, совпадает ли снаряд с попаданием, читается ли иконка на HUD,
нет ли засветки за FOV, удобно ли целиться. OpenGL-драйвер, звук на устройстве
и визуальная оценка не покрываются headless-тестами. Для редакторов проверять
не только import, но и открытие/сохранение соответствующего формата.
